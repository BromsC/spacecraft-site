# CLAUDE.md — standing instructions for Claude Code sessions

## Project

**The Space Craft** — website for an ongoing exhibition in Stockholm. Content: the exhibition
itself, the current artists, light visuals. No e-commerce, no auth, no backend.

- Domain: `thespacecraft.se` (DNS at GoDaddy, hosted on GitHub Pages)
- Repo: `BromsC/spacecraft-site`
- Content editing: TinaCMS (Tina Cloud backend), admin at `/admin`

## Working model

- **All building happens in Claude Code sessions.**
- **All discussion/consultation happens in a separate claude.ai Project**, which reads this repo
  at the start of every chat to learn the current state. The repo must be self-describing;
  `docs/STATE.md` is the handoff document and must always be accurate.
- **Caspar works browser-only.** Never ask him to run anything locally. Everything must work via
  `git push` + GitHub Actions. Anything he must do should be a click in a web UI
  (GitHub settings, Tina Cloud dashboard, GoDaddy DNS) and spelled out step by step.

## SESSION START (mandatory)

1. Read `docs/STATE.md` and `docs/DECISIONS.md` before doing anything else.
2. Check the latest GitHub Actions run if the task touches build/deploy.

## SESSION END (mandatory)

1. Rewrite `docs/STATE.md` so it reflects reality (date, status, routes, in progress, next steps,
   open questions, known issues, secrets status). Never end a session with STATE.md stale.
2. Append any new decisions to `docs/DECISIONS.md` (never edit or delete old entries — supersede
   them with a new entry).
3. Run `npm run build:site` and `npx astro check`; both must pass.
4. Commit with a conventional-commit message (`feat:`, `fix:`, `docs:`, `chore:`, `ci:` …) and
   push to `main`. If the environment only allows a feature branch, push that, open a PR, and say
   so in the final message.

## Stack

- Astro (static output only), TypeScript (strict), npm
- TinaCMS (`tinacms` + `@tinacms/cli`), Tina Cloud backend, standard admin editing (no visual
  editing). React/react-dom are installed only because Tina's admin build needs them — the site
  itself ships no React.
- Content: Markdown/JSON + frontmatter under `content/`, read by Astro content collections
  (`glob` loader) — the same files Tina edits.
- Styling: plain CSS with custom properties (`src/styles/global.css`). No Tailwind, no UI framework.
- Deploy: GitHub Actions (`.github/workflows/deploy.yml`) → GitHub Pages. Custom domain via
  `public/CNAME`.

## File layout

```
content/                 # all editable content (Tina writes here, Astro reads here)
  site/settings.json     # singleton: site title, tagline, social links, footer
  exhibition/current.md  # singleton: the current exhibition
  artists/*.md           # one file per artist; filename = URL slug
  pages/*.md             # generic pages (about, …); filename = URL slug
public/
  CNAME                  # thespacecraft.se — do not remove
  uploads/               # Tina media root (images uploaded via the CMS land here)
  admin/                 # generated by `tinacms build` in CI — gitignored, never commit
src/
  content.config.ts      # Astro collections — must mirror tina/config.ts
  lib/content.ts         # data helpers (getSiteSettings, getExhibition, getArtists, …)
  layouts/Layout.astro   # shared shell: header nav + footer from site settings
  components/            # .astro components (PascalCase filenames)
  components/visual/     # client-only visual islands (Three.js etc. later)
  pages/                 # routes: index, artists/index, artists/[slug], [slug], 404
  styles/global.css      # design tokens (:root) + global styles
tina/
  config.ts              # Tina schema — must mirror src/content.config.ts
  tina-lock.json         # generated schema lock — COMMIT it (Tina Cloud reads it)
  __generated__/         # gitignored
docs/
  STATE.md               # current state / handoff — keep accurate
  DECISIONS.md           # append-only decision log
```

## Conventions

- Filenames: content files and routes are `kebab-case`; components are `PascalCase.astro`.
- Image fields store public paths (`/uploads/foo.jpg`) as plain strings; render with `<img>`.
- Scripts: `npm run build:site` (Astro only, no Tina — what to use to verify), `npm run build`
  (Tina + Astro, needs Tina secrets), `npm run dev`, `npx astro check`.
- Keep `npm run build:site` and `npx astro check` at zero errors and zero warnings.
- Content entry ids come from filenames. Don't add a `slug` frontmatter field — Astro's glob
  loader would use it as the id and it would drift from the filename Tina manages.

### Add a content collection (Tina + Astro)

1. Create the folder `content/<name>/` with at least one seed file.
2. Add the collection to `tina/config.ts` (`name`, `label`, `path: 'content/<name>'`, `format`,
   `fields`). For a singleton add `match: { include: '<file>' }` and
   `ui.allowedActions: { create: false, delete: false }`.
3. Add the matching collection to `src/content.config.ts` with
   `glob({ pattern: '**/*.md', base: './content/<name>' })` and a zod schema whose fields mirror
   the Tina fields (optional in Tina → `.optional()` / `.default()` in zod).
4. Add a helper in `src/lib/content.ts` if pages will need it.
5. `npm run build:site` + `npx astro check`. Note the change in STATE.md.

### Add a page

- **Editable text page** (About, Info, Visit…): add `content/pages/<slug>.md` with a `title`
  frontmatter field. It is served at `/<slug>` by `src/pages/[slug].astro`. Avoid slugs that clash
  with real routes (`artists`, `admin`, `uploads`, `404`).
- **New route with its own layout**: add `src/pages/<route>.astro`, wrap in `<Layout title="…">`.
  If it should be in the nav, edit the `nav` array in `src/layouts/Layout.astro`.

### Add a visual island

See `src/components/visual/README.md`. In short: an `.astro` component in
`src/components/visual/` with a `<script>` that dynamically imports the heavy library, starts on
visibility, respects `prefers-reduced-motion`, and has a static fallback. Adding `three` (or any
framework integration) is a new dependency → log it in DECISIONS.md.

## Constraints

- Static output only. No SSR adapter, no server endpoints, no backend.
- Never give Caspar local-run instructions (no "run npm …", no "clone the repo").
- No new dependencies without a DECISIONS.md entry (what, why, alternatives).
- CI must keep working without Tina secrets (the Tina build step is conditional).
- Don't commit secrets. `.env` is gitignored; `.env.example` documents the variables.
